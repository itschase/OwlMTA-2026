## What it does

`account` owns the inherited username/password registration and login interface, the optional existing-link Discord login bridge, account/session element data, tutorial and application gates, character quota/create/list/select/spawn/change/logout, account and character F10 settings, email capture, news/rules presentation, saved client preferences, and an obsolete forum-link path.

The source now has two entry paths into one account-admission function. Password login proves the submitted credential; the optional Discord path asks the separately installed `mta-discord-identity` adapter for a connection-bound challenge and one-use ticket, then accepts only its opaque linked-account reference. Both paths load the Core row and run activation, ban, serial/device, MTA account-details, and duplicate-session checks before publishing account state. Character selection or creation then leads into the large multi-resource hydration and spawn. Character change saves and clears state before returning to selection.

This is a fixed-in-source existing-link login/session slice, not a completed Discord authentication deployment. A Discord proof now produces only a pending server-held activation ticket; Owl stages and revalidates local admission before the adapter caches a bounded capability session and before Owl publishes login state. It does not provision accounts, expose a general gameplay capability facade, disable legacy password login, persist identity links durably, or disconnect an admitted Owl session after authorization loss. Those boundaries remain open in Issues #2, #3, #68, #96, and #551; no Discord application, identity service, or MTA runtime was exercised.

## Player, staff, and operator use

- The login panel accepts registration or returning credentials and can remember only the username locally. When the compatible reusable adapter resource is running, it also displays **Sign in with Discord (linked accounts)**. That flow copies a normal-browser verification URL/code and accepts the one-time ticket returned after authorization; it does not ask the player for an account or Discord ID. Character selection lists owned active characters; creation collects roleplay identity and appearance before a server-selected starting location.
- Normal character selection binds the requested character ID to the authenticated account. Recent F10 settings code uses server-side actor/account/character binding plus per-setting allowlists and normalization; Issue #79 remains open until runtime validation and every writer are reconciled.
- Authorized staff can use `/loginto` to enter another account's character. Rules, news, and patch-note update commands are also present. These actions require capability/audit redesign; donor/supporter status must remain separate from staff authority.
- Operators need both Core and MTA schemas plus a long dependency chain including `mysql`, `anticheat`, `global`, `integration`, `cache`, `pool`, `item-system`, `factions`, `logs`, `donators`, `bans`, `serialwhitelist`, `prison-system`, and spawn-time feature resources.

## Credential, privacy, and lifecycle findings

- New registration uses bcrypt-sha256; accepted legacy salted double-MD5 credentials are upgraded in place. The login panel now remembers only the username, removes a legacy password node when loading the preference file, and no longer sends the password back to the client for persistence. [Issue #528](https://github.com/itschase/OwlMTA-2026/issues/528) remains open for disposable-client verification of existing-file cleanup and the old-to-private XML migration.
- Login and registration events are remotely callable. The server caps login fields, applies the registration username/password/email rules before hashing or database work, and uses in-memory per-player and per-IP request budgets (login: 10/player/minute and 40/IP/minute; registration: 3/player/10 minutes and 10/IP/hour). Discord challenge creation shares the login budget instead of relying only on the identity service's installation-wide allowance; ticket exchange remains subject to the identity service's per-challenge limit. Unknown usernames and incorrect legacy/current passwords now receive the same player-facing failure; the premature `Password Accepted` message is removed. Ban lookup and its staff/log side effects run only after credential proof. A ban-query failure now blocks login rather than being treated as no ban. Database start/failure, disconnect, credential rejection, inactive account, ban, ban-check failure, and legacy-upgrade failures have credential-free server outcome codes. These are source changes only; username timing differences, timer behavior, NAT impact, and request pressure remain runtime-unverified. [Issue #529](https://github.com/itschase/OwlMTA-2026/issues/529) remains open for timing-resistant handling and disposable stress/forged-event verification; [Issue #160](https://github.com/itschase/OwlMTA-2026/issues/160) owns wider ban enforcement and outage behavior.
- Registration writes `core.accounts` and MTA `account_details` separately and calls an absent localhost activation-mail service. Issue #43 owns partial cross-schema provisioning; Issues #12/#13 own forum and activation dependencies.
- The email-change event previously trusted a client-supplied account ID and had no authenticated-session boundary. The source now derives the account from the logged-in server session, validates and parameterizes the update, synchronizes the email only after DB success, and returns the actual result. [Issue #527](https://github.com/itschase/OwlMTA-2026/issues/527) remains open for runtime, duplicate-address, and DB-failure validation. No active password-recovery consumer was found, so takeover impact is not established.
- Login now checks the serial-whitelist policy using the authenticated account row before displacing another session or setting account identity/ranks/session element data. A denied device login therefore does not inherit partial authenticated state or kick an already-connected account. Issue #158 remains open for in-game enrollment/revocation, policy cleanup, and runtime verification.
- Password and Discord-linked login now share one account-admission function. It requires an active Core account, a successful current ban check, accepted serial/device policy, and usable `account_details` before displacing another session or setting `account:loggedin`. The previously malformed missing-`account_details` creation call is corrected, its reload is checked, and serial/IP updates are parameterized. Privacy-conscious diagnostics record only admission method and bounded outcome names. This is source-only and tracked by #551/#68; query timing, GUI behavior, resource ordering, and every failure race remain runtime-unverified.
- Discord admission is two-phase in source. The standalone adapter keeps the activation ticket and binds it to the host resource/player generation; Owl stages account data, requests activation only after local gates pass, then reloads Core and repeats activation/ban/device/account-details checks before committing. Activation failure, local revalidation failure, adapter stop, cancel, or disconnect clears pending state without granting local login. The cached capability/donor result remains server-only and currently has no general Owl gameplay authorization facade.
- The Owl bridge validates both `sourceResource` and event source against the running reusable adapter, while its remotely callable begin/exchange/cancel events derive the player only from MTA's `client`. It accepts no client account/Discord identifier and never receives the adapter-held connection token. The Discord button is hidden when the compatible adapter exports are absent, so Owl boot and password operation do not depend on that optional resource.
- After an account resource restart, `account/s_main.lua:onJoin` preserves existing `loggedin` and account state if `account_details` contains the account ID, then `account/s_login.lua` consumes a one-use local seamless flag without rechecking activation, ban, serial, authorization generation, or session age. The Discord adapter/session lease boundary belongs to Issues #68 and #96; no bounded lease exists in current Owl source.
- Login synchronizes email, credits, staff/support ranks, punishment, admin-jail, and related account data more broadly than minimum gameplay need. Server-only session claims and field-level synchronization need an explicit consumer inventory.
- Shared hash constants are shipped in a client-loaded file. Any intended secret is therefore public to every connecting client and must be removed or replaced.
- Character creation performs quota lookup, name lookup, insert, logging, and temporary state changes as separate operations. Concurrent or failed requests lack a durable idempotency/reconciliation boundary.
- Character spawn is a long side-effectful hydration sequence. Dependency/DB failure after state is cleared can strand a partial character session.
- The spawn-correction remote accepts a client-provided expected location and can teleport from the selection area; correction must come from stored server state or a server-issued one-use context.
- The obsolete forum-login path transmits a forum password and depends on missing legacy integration. It should be retired under the Discord/website-independent identity work, not rebuilt as a parallel login system.

The account login preference cleanup uses MTA's XML node and file APIs: [xmlDestroyNode](https://wiki.multitheftauto.com/wiki/XmlDestroyNode) removes the legacy password node from the loaded tree, and [xmlSaveFile](https://wiki.multitheftauto.com/wiki/XmlSaveFile) persists that change. The server-to-client preference event now passes only the username; [triggerClientEvent](https://wiki.multitheftauto.com/wiki/TriggerClientEvent) documents its argument-passing behavior. The login query follows MTA's asynchronous [dbQuery](https://wiki.multitheftauto.com/wiki/DbQuery) callback pattern; [dbPoll](https://wiki.multitheftauto.com/wiki/DbPoll) documents that a failed query result frees its handle automatically. This API review does not substitute for a disposable-client/database check.

## Target direction

Continue from the fixed-in-source existing-link admission/session slice toward a server-only Owl capability facade; revocation-driven disconnects; durable identity storage; immutable internal account IDs linked to verified Discord identities; supporter tiers as separate entitlements; staged/idempotent provisioning; one canonical active-character session; minimal client claims; audited staff impersonation; and recoverable character creation/change/spawn phases. Local password verification should remain only as a bounded, audited migration or owner-recovery mechanism until retired.

Bounded implementation work is tracked by [Issue #201](https://github.com/itschase/OwlMTA-2026/issues/201) for client-shipped hash constants, [#202](https://github.com/itschase/OwlMTA-2026/issues/202) for atomic character creation, [#203](https://github.com/itschase/OwlMTA-2026/issues/203) for staged spawn hydration, and [#204](https://github.com/itschase/OwlMTA-2026/issues/204) for server-derived spawn correction. Existing Issues #2, #43, #74, #79, and #158 retain identity, provisioning, protected-data, settings, and device-session ownership.

Runtime verification must cover legacy hash upgrade and bcrypt boundaries; remember-me migration; activation/provisioning partial failures; duplicate/concurrent registration; Discord challenge display/copy/cancel/expiry/reconnect/replay/wrong-ticket/service-outage flows; serial/ban/account-details/duplicate-session ordering through both login methods; identity and account resource restart; character ownership/quota/name/concurrent creation; every spawn hydration failure point; forged correction coordinates; settings type/allowlist/persistence; privacy synchronization; donor/supporter/staff isolation; `/loginto` hierarchy/audit; and independent Core/MTA DB outages.
